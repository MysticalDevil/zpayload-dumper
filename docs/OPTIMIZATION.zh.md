# zpayload-dumper 优化演进笔记

> 这是一篇给开发者看的"白话技术笔记"，记录了这个项目从"慢"到"快"的完整思考过程。

---

## 一、先搞清楚：我们在解决什么问题？

Android 手机的系统更新包（OTA）里有一个 `payload.bin` 文件。它里面装着新系统的所有分区数据
（比如 `system`、`vendor`、`product`、`boot` 等）。

这个文件的结构 roughly 是这样的：

```text
payload.bin = [头部信息] + [操作1] + [操作2] + [操作3] + ...
```

每个**操作**（Operation）告诉提取器：

- 从文件的哪个位置读取一段压缩数据
- 用什么算法解压（不压缩 / xz / bzip2 / zstd）
- 解压后写到输出文件的哪些位置（这叫"extent"，可以理解成"数据块"）
- 数据的 SHA-256 校验值

**关键问题**：一个分区可能有几百甚至几千个操作。比如 `product` 分区 (~4GB) 可能有上千个操作。

---

## 二、方案一：基线版本（`3f22fea`）— 一个分区一个线程

### 怎么工作的？

```text
主线程：
  读取 payload.bin 的头部，知道有哪些分区
  对每个选中的分区：
      开一个线程 → 提取这个分区的所有操作
  等所有线程结束

工作线程（每个分区一个）：
  打开 output.img（输出文件）
  逐个处理操作：
      1. 跳到 payload.bin 里对应的位置
      2. 把数据解压到内存
      3. 用 ExtentCursor 把数据写到 output.img 的正确位置
      4. 校验 SHA-256
```

### 优点

- **简单**：代码好写，不容易出 bug
- **不用锁**：每个分区有自己的输出文件，线程之间互不干扰
- **不浪费磁盘空间**：数据从压缩包直接解压到最终文件，没有中间文件

### 缺点（致命的）

假设你要提取 `system`、`vendor`、`product`、`system_ext` 这 4 个大分区。CPU 有 16 个线程，但这里只用了 **4 个线程**。

那个 4GB 的 `product` 分区被一个线程慢慢啃，其他 12 个线程在旁边围观。

就像一家餐厅有 16 个厨师，但菜单上只有 4 道菜，每道菜只能由一个厨师做。就算其他厨师闲着，也没人帮忙。

### 性能

| 场景 | 耗时 | 速度 |
|------|------|------|
| 提取 4 个大分区 (system) | 100 秒 | 61 MiB/s |
| 提取全部 24 个分区 (full) | 101 秒 | 65 MiB/s |

---

## 三、方案二：保守优化（`d731df5`）— 小修小补

基线版本太慢了，我们尝试了三项"小优化"，不改架构：

### 1. Extent 合并

把相邻的 extent 合并成更大的 extent，减少 `seek`（跳转磁盘位置）的次数。

**结果**：没效果。因为 Android OTA 生成的 extent 本来就已经很大了（几 MB 到几十 MB），合并前后 seek 次数差不多。

### 2. 排序调度

按分区大小排序，让大分区先开始提取。这样小分区可以在大分区还在跑的时候并行处理。

**结果**：没效果。4 个大分区几乎同时开始、同时结束，谁先谁后差别不大。

### 3. 缓冲区复用

每个线程的解压缓冲区只分配一次，反复使用，减少内存分配器的压力。

**结果**：没效果。基线版本的内存分配本来就不是瓶颈。

### 学到的教训

> 如果瓶颈是"一个厨师做一道菜"，那么给厨师换一把更快的刀（extent 合并）、让大菜先上（排序调度）、或者让厨师不用每次都洗围裙（缓冲区复用）——都不会让餐厅上菜更快。
>
> **真正的瓶颈是：菜太多，厨师太少。**

## 四、方案三：激进优化（`face5a8`）— 临时文件方案

### 核心思路

#### 打破"一个分区一个线程"的限制

把所有分区、所有操作，全部摊平成一个巨大的任务列表。然后开 16 个工人线程，谁有空谁拿一个任务来做。

```text
任务列表（全局队列）：
  [分区0, 操作0], [分区1, 操作0], [分区0, 操作1], [分区2, 操作0], ...

16 个工人线程：
  每个线程原子地取一个任务编号（fetchAdd）
  解压数据 → 写到临时文件
  等所有工人干完活

主线程（合并阶段）：
  对每个分区：
      按顺序读取临时文件
      把数据合并到最终的 output.img
      删掉临时文件
```

### 临时文件的生命周期

```text
Worker A 解压了 [product, 操作123]
    → 写入 /tmp/.zpayload_tmp/product/op123.tmp

Worker B 解压了 [system, 操作456]
    → 写入 /tmp/.zpayload_tmp/system/op456.tmp

...（几百个临时文件同时存在）

合并阶段：
    打开 product.img
    读取 op0.tmp → 写入 product.img
    读取 op1.tmp → 写入 product.img
    ...
    删掉所有 tmp 文件
```

### 优点

- **终于能用满所有 CPU 了！** 16 个线程同时解压，不管它们属于哪个分区
- **在"少量大分区"的场景下非常快**

### 缺点（也是致命的）

每个操作都要：

1. 写一个临时文件到磁盘
2. 合并时再读一次临时文件

对于 `full` 全量提取（24 个分区）：

- 最终输出：~6.9 GB
- 临时文件峰值：也 ~6.9 GB
- 实际磁盘写入量：**~13.8 GB**

而且合并阶段是**单线程**的（每个分区一个线程按顺序读临时文件），这意味着：

- 即使 16 个工人已经干完了，主线程还要花很长时间逐个合并
- 几百个临时文件同时存在，磁盘要不停地"创建→写入→读取→删除"

### 性能

| 场景 | 耗时 | 速度 | 备注 |
|------|------|------|------|
| 4 个大分区 (system) c=1 | 51.8 秒 | 119 MiB/s | ✅ 很快 |
| 全部 24 个分区 (full) c=1 | **146 秒** | **44 MiB/s** | ❌ 比基线还慢！|

### 为什么 full c=1 反而更慢？

因为临时文件的 I/O 开销太大了。基线版本虽然只有一个线程一个分区，但数据是"一次写入"；
临时文件方案虽然解压并行，但数据要"写两次"（临时 + 最终）。

当分区很多时，临时文件的数量爆炸，磁盘随机 I/O 把性能拖垮了。

## 五、方案四：流式优化（`f4c06a0`）— 直接写入（最终方案）

### 核心 insight

临时文件方案的问题是：**把解压和写最终文件分开了**。

能不能让工人解压完后，**直接写到最终文件**？这样就没有临时文件了！

但有个难题：一个分区里的操作必须**按顺序写**。比如操作 0 必须先写完，才能写操作 1，因为后面的操作可能覆盖前面的位置。

如果工人 A 在做操作 0，工人 B 在做操作 1，B 可能比 A 先做完。那 B 不能提前写，否则顺序就乱了。

### 解决方案："对号入座" + 内存缓冲

给每个分区维护一个"下一个该写的操作编号"（`next_expected_op`）。

```text
分区 product 的状态：
  next_expected_op = 0    ← 现在轮到操作 0 写入了
  pending = []            ← 已经解压完但还不能写的操作，暂存这里

工人 A 做完 [product, 操作0]：
  " next_expected_op 正好是 0，我可以直接写！"
  → 直接把解压后的数据写到 product.img
  → next_expected_op 变成 1
  → 检查 pending：操作 1 在里面吗？
      → 在！拿出来写掉
      → next_expected_op 变成 2
      → 检查 pending：操作 2 在里面吗？
          → ...继续连锁反应

工人 B 做完 [product, 操作5]：
  " next_expected_op 是 2，我还没轮到我"
  → 把数据放到 pending 里
  → 等待

工人 C 做完 [product, 操作2]：
  " next_expected_op 是 2，轮到我啦！"
  → 直接写到 product.img
  → 连锁检查 pending 里的操作 3、4、5...
```

### 内存不够怎么办？

如果 pending 里的数据太多，内存会爆。所以设置了一个**全局内存预算**：256 MB。

```text
工人 B 要把 [product, 操作5] 放进 pending：
  申请 10 MB 内存预算
  ├─ 预算够用：数据复制到内存，放进 pending
  └─ 预算不够：把数据写到一个很小的临时文件（spill），只存文件路径到 pending
```

因为操作通常**大致按顺序**被处理（任务队列虽然是全局的，但大分区的操作很多，
工人大概率是交错处理不同分区的操作，同分区的操作往往接近顺序），
所以 **pending 很少被用到，临时文件 spill 更罕见**。

### 数据流对比

#### 临时文件方案

```text
payload.bin → [解压] → 临时文件 → [读取] → ExtentCursor → output.img
         写了 6.9 GB 临时文件    读了 6.9 GB 临时文件
```

#### 流式方案

```text
payload.bin → [解压] → 内存 buffer ─┬─ 按序？→ 直接 ExtentCursor → output.img
                                    └─ 乱序？→ pending（内存，最多 256MB）
```

**没有大规模临时文件！** 磁盘只写最终输出，I/O 量减少了一半。

### 代码层面的关键设计

```zig
// 每个分区的写入状态
PartitionWriteState {
    output_file: File,           // 打开的最终输出文件
    next_expected_op: Atomic(0), // 下一个该写的操作编号
    pending: Mutex + ArrayList,  // 暂存的乱序操作
}

// 全局内存预算
MemoryBudget {
    remaining: Atomic(256MB)     // CAS 原子扣减
}

// 工人主循环
while (true) {
    task = 从全局队列取一个任务
    data = 解压操作到 ArrayList

    加锁(partition)
    if (task.op_index == partition.next_expected_op) {
        解锁
        直接写 data → output_file（通过 ExtentCursor）
        加锁
        next_expected_op += 1
        连锁 flush pending
        解锁
    } else {
        if (内存预算.tryAcquire(data.len)) {
            pending.append(内存副本)
        } else {
            tmp_path = 写临时 spill 文件
            pending.append(tmp_path)
        }
        解锁
    }
}
```

### 为什么这个方案这么快？

1. **并行解压保留了下来**（16 个工人同时干活）
2. **临时文件税被消灭了**（数据直接从解压器流向最终文件）
3. **合并阶段也消失了**（写入是实时、交错的，不用等所有解压完成）

### 性能

| 场景 | 耗时 | 速度 | vs 基线 | vs 临时文件 |
|------|------|------|---------|-------------|
| 4 个大分区 (system) c=1 | **18.3 秒** | **337 MiB/s** | +445% | +183% |
| 全部 24 个分区 (full) c=1 | **18.3 秒** | **359 MiB/s** | +452% | +718% |
| 全部 24 个分区 (full) c=8 | **21.9 秒** | **300 MiB/s** | +206% | +206% |

full c=1 从 146 秒（临时文件）降到 18.3 秒（流式）——快了 8 倍！

## 七、学到的经验

### 1. 先定位瓶颈，再动手优化

我们一开始尝试了 extent 合并、排序调度、缓冲区复用——都没用。因为它们优化的是"刀够不够快"，而真正的瓶颈是"厨师够不够多"。

如果没有性能分析（profiling），优化就是盲目射击。

### 2. 并行化很好，但要注意 I/O 代价

临时文件方案证明了并行解压的价值，但也暴露了一个陷阱：**并行计算的好处可能被 I/O 开销完全抵消**。

写临时文件再读回来，磁盘做了双倍工作。对于 SSD 来说，顺序写很快，但"几百个小文件的创建+写入+读取+删除"会产生大量随机 I/O，拖慢整体速度。

### 3. 流式（streaming）通常优于批处理（batch）

临时文件方案是**批处理**思维：先全部解压完（Phase 1），再全部合并（Phase 2）。

流式方案是**流水线**思维：解压和写入交错进行，数据"流动"过系统，不在中间停留。

批处理需要存中间结果，流水线不需要。这是性能差异的核心原因。

### 4. 内存是磁盘的高速缓存

流式方案用 256 MB 内存作为"弹性缓冲"，吸收了偶尔的乱序，避免了落盘。这是经典的**用空间换时间**策略。

在内存充足（现代电脑通常有 16GB+）的情况下，256 MB 的缓冲代价极小，但省去了大量磁盘 I/O，收益巨大。

### 5. 提前失败比中途失败好

新加的磁盘空间检查（`statvfs`）在提取开始前就告诉用户"空间不够"。这比提取到一半报错要好得多——后者可能留下一堆半成品文件，用户也不知道该删什么。

## 八、给想学习的人的推荐阅读顺序

1. 先看 `src/payload/engine.zig` 的 `run()` 函数——这是整个提取流程的入口
2. 再看 `PartitionWriteState` 和 `MemoryBudget`——理解流式写入的核心状态
3. 看 `workerMain()`——理解工人如何从全局队列取任务、解压、并决定"直接写"还是"进 pending"
4. 看 `flushPending()`——理解连锁触发机制
5. 最后看 `extent_writer.zig` 的 `ExtentCursor`——理解数据是如何按正确位置写入输出文件的
